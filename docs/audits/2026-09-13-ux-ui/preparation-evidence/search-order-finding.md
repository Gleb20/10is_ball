# F-PREP-001 — Порядок имени меняет результат поиска

**Основание:** runtime_defect + экспертная интерпретация последствий; confidence high для воспроизведения, частота в реальной аудитории unknown. P2: допустимого человека нельзя найти привычным полным именем в одном из повторяющихся селекторов. Каноническая задача BUG-023. Это ограниченная диагностика компонента на candidate, не прохождение основного UX pilot.

**База:** GAP-012 r3 app bytes, frozen export c60920f545e007ec656ee88194430acd6999558e7a531edb4f1904a22ad91b5e; r4–r6 меняют только E2E. Chromium153.0.8010.12, desktop1440×900, обычный synthetic organizer C, localhost4617/4618, disposable PG. Участник synthetic active, никогда не входил, mustChangePassword=true; это не исключает его из directory.

**Воспроизведение:** открыть roster collecting-турнира с consent=true; в «Добавить игрока» ввести «Поздний» — доступна option «Синтетический Поздний»; заменить на «Поздний Синтетический» — options0, объяснения отсутствия результатов нет. В MatchCreate «Игрок A» тот же полный запрос даёт option «Поздний Синтетический». Участник при диагностике не добавлялся, матч не создавался.

**Evidence:** [API/account proof](new-account-directory.json), [DOM comparison](name-order-browser.json), [viewport](name-order-browser.png). [MatchCreate comparison](name-order-match.json) и [кадр поля и результата после ручной прокрутки](name-order-match-visible.png) записаны отдельно; это наблюдение координатора, не пользовательский тест. Первый name-order-match.png оставлен как контекстный кадр: поле и option в нём перекрыты/вне viewport, он не доказывает видимость результата. Дополнительная ручная прокрутка во втором кадре не считается исправлением BUG-019. Source: UserPicker использует directory displayName LAST FIRST; MatchCreate собирает FIRST LAST; Autocomplete фильтрует label по цельной подстроке на клиенте. Не относить этот результат к серверному поиску.

**Последствие:** пользователь может решить, что игрок отсутствует или недоступен, хотя поиск по одному имени его показывает. Состояние «нет результата» также не объяснено. Это гипотеза пользовательской интерпретации, а не дословное интервью.

**Минимальный target:** искать введённые фрагменты имени независимо от их порядка; каждый фрагмент должен встречаться в видимом label. Ноль совпадений при непустом запросе получает явное сообщение. Выбор по stable ID, полномочия, exclusions и форма отображения имени сохраняются. Общую унификацию отображаемых имён рассматривает синтез RESULTS; она не нужна для исправления поиска.

**Перепроверка:** на окончательно принятой GAP-012 базе и mobile390, с клавиатурой/касанием; несколько совпадений и одинаковые имена. Частотность и привычный порядок ввода уточнить в интервью без подсказки.
