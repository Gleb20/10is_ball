# Проверка исхода записи очка

Target BUG-029 принят Terra и координатором по точному version/key контракту; см. [review](core-review.json). [Личное воспроизведение](coordinator-rechecks/judge-outcome/README.md) подтверждает риск повторного пользовательского действия после уже сохранённого очка. Это не изменение правил подсчёта и не утверждение об автоматическом дублировании.

## Сохраняемые данные и различение исходов

При отправке сохранить конкретное намерение: сторону, idempotency key и отправленную expectedVersion. При ошибке не терять эту связь. Оставшиеся нажатия, которые ещё не отправлялись, учитывать отдельно с их порядком и количеством по сторонам. Не показывать их как уже начисленные очки и не отправлять автоматически после ошибки.

Первый шаг восстановления — чтение authoritative match. Текущий getMatch возвращает полные idempotencyKeys/eventLog: точное наличие отправленного ключа доказывает применение этого запроса. Рост общего счёта или версии этого не доказывает. Отсутствие ключа в раннем GET тоже не доказывает отказ: старый POST ещё мог не завершиться.

| Исход | Сообщение и следующий шаг |
|---|---|
| Ключ найден в authoritative ответе | «Очко сохранено. Счёт X:Y». Повтор этого очка не предлагается; состояние матча определяет дальнейшие доступные действия |
| Получен окончательный no-write отказ по действующему API контракту | Понятная причина. После получения актуального состояния возможен только явный новый запрос; при утрате прав он недоступен |
| Сеть/потерянный ответ/5xx либо чтение не удалось | «Не удалось проверить, сохранилось ли последнее очко». Кнопка «Проверить счёт», состояние ожидания и последнее подтверждённое значение |
| Смена владельца/утрата сессии/матч завершён | Существующий lost-lock/reauth/terminal flow. Ни повтор, ни захват управления скрыто не происходят |

После ошибки блокировать новые score/Undo/correction/finish mutations до сверки. Видимые неотправленные нажатия не пропадают молча: «Не отправлено ещё N нажатий: A — n, B — m». Успешное чтение не является разрешением автоматически воспроизвести очередь. Таймер, стороны, подача и последний подтверждённый счёт остаются видимы. Проверка GET имеет single-flight и не дублируется background refresh. Возвращение сети запускает только разрешённую текущим D27 синхронизацию чтения.

## Явное решение после успешного чтения

Если точный ключ найден, можно возобновить ведение из authoritative состояния. Неотправленная очередь показывается отдельным блоком с «Отправить оставшиеся нажатия» и «Не отправлять». Первый вариант — явное подтверждение пользователя, сохраняет прежний порядок и поочерёдную отправку; второй требует подтверждения отказа от этих нажатий и ничего не записывает. Если match уже не принимает очки, отправка недоступна, а количество неотправленных нажатий всё ещё видно при проверке результата.

Если чтение успешно, но точный исход ещё неизвестен, показать счёт и два явно разных решения: «Принять показанный счёт» и «Начислить последнее очко стороне {A/B}». Оба требуют отдельного подтверждения показанного счёта; без успешного GET они недоступны. Это решение человека о реальном игровом счёте, а не выдача отсутствующего ключа за техническое доказательство отказа.

Безопасность второго действия обязательна: новое намерение использует новый ключ и **именно ту expectedVersion, которую человек только что проверил**. Background refresh не подменяет её перед отправкой. Если исходный задержанный запрос успел изменить состояние, новый запрос получает version conflict и не начисляет второе очко. Если новый запрос успел раньше, исходный запрос со своей старой expectedVersion не может позже добавить ещё одно. Любой conflict снова требует чтения и решения; нельзя автоматически переназначить новую version и повторить запрос. Эта гарантия должна быть проверена на реальном PostgreSQL в обоих порядках завершения.

«Принять показанный счёт» не выполняет mutation. Дальше работают обычные новые намерения и version guards. Неотправленные нажатия обрабатываются отдельным явным выбором, как описано выше. После каждого подтверждённого результата учитывать актуальные status, владение сессией и доступность ввода; не включать +1 при pending_confirmation/finished.

## Отображение и ограничения

Блок восстановления расположен после краткого статуса и перед табло, в пределах текущей immersive композиции. Это не модальное окно поверх счёта. Текст ошибки использует принятый BUG-024 контраст; подтверждение чтения — role=status, неопределённость — доступное сообщение без кода Failed to fetch. После завершения запроса фокус не теряется, а новые сообщения объявляются без постоянного перехвата ввода.

Не менять reducer, правила подачи/победы, server authorization, idempotency semantics, единственного активного судью или статистику. Не добавлять offline queue, optimistic очки, автоматический POST retry или новый endpoint. Если текущий контракт не гарантирует полноту keys/монотонность version, остановить реализацию этой части и сначала уточнить контракт; неопределённость не маскировать эвристикой score delta.

## Приёмка

1. Commit→потеря ответа→GET с exact key: видно сохранённое очко, нет команды повторить его и нет второго POST.
2. Известный окончательный отказ: причина понятна, retry явный; проверяются авторизация и актуальная версия.
3. GET при незавершённом POST без ключа остаётся unknown. Для явного начисления проверить оба порядка original/new transaction; максимум одно засчитываемое очко, либо явный conflict, никогда скрытый rebase.
4. GET сам падает: старый счёт виден, score mutations закрыты, повтор только чтения. После online нет автоматического score POST.
5. Несколько быстрых нажатий до сбоя: отправленное неопределённое и ещё не отправленные различимы; подтверждение/отказ от остатка не теряют и не дублируют намерения.
6. Граница pending_confirmation, чужая auth session, handover,401 и final state сохраняют существующие guards. Повторный клик recovery не создаёт второй запрос.
7. Проверить desktop1440/mobile390, keyboard/focus, narrow/landscape и accessible announcements. Реальные пользовательские частоты не выводить из автоматизированного прогона.

Для реализации это critical journey: компонентные/state tests, реальные PostgreSQL ordering cases и repository-wide gate с браузерными сценариями обязательны. Алгоритм и контракт приняты; BUG-029 ready для реализации, а не implemented.
