# Ошибка и ожидание в диалоге построения сетки

Статус: предложение после подтверждённых F-CMP-SUP-001/002. BUG-021 описывает определённый целевой результат ошибки; BUG-022 ждёт решения Q-UX-001 о закрытии во время запроса. Это не исправленный интерфейс и не общая политика всех модальных окон.

## T-DIALOG-ERROR-001 — Ошибка в активном контексте

Сохранить Dialog открытым, выбранный алгоритм и текущий roster. Ошибку операции выводить **внутри** Dialog после вариантов алгоритма и перед кнопками. Пока Dialog открыт, ту же ошибку не объявлять второй раз из скрытой подложки. Независимые ошибки страницы остаются ошибками страницы.

```text
390px: существующая ширина и поля Dialog
┌ Как построить сетку?                 × ┐
│ Компактная / Классическая              │
│ существующие пояснения и выбор         │
│                                       │
│ ! Не удалось построить сетку.          │ ← alert, виден без выхода из Dialog
│   Причина и доступное следующее действие│
│                                       │
│ [Отмена]             [Повторить]        │ ← только при известном отказе
└───────────────────────────────────────┘

desktop: те же блоки в существующем Dialog;
варианты сохраняют текущую раскладку, error занимает общую строку.
```

При известном серверном отказе primary action «Повторить» повторяет явно выбранную пользователем операцию. Автоматического повторения POST нет. При неизвестном исходе из-за потери ответа сначала «Проверить состояние» выполняет GET; если сетка уже построена, показать актуальный результат вместо повторной генерации. Если read также не удался, сохранить понятное неопределённое состояние; не писать «изменений нет» без доказательства.

После появления ошибки фокус/прокрутка должны дать доступ к сообщению и следующему действию внутри Dialog. Нельзя оставлять единственную ошибку за inert overlay. При длинном тексте сохраняется scroll внутри Dialog; footer остаётся достижимым на360/390 и при увеличении масштаба. Не менять текущую геометрию окна ради декоративного обновления.

Неприменимые права/статус турнира — объяснить как отказ с выходом к актуальным данным; кнопка «Повторить» не должна обещать исправить FORBIDDEN/уже начатый турнир. Параметры алгоритма и участников сервер перепроверяет по прежним правилам.

## T-DIALOG-PENDING-001 — Решение пока открыто

Факт: inputs/footer отключены, а Close выглядит активным и фокусируется, хотя callback игнорирует click/Escape. Это несогласованное состояние. Простое отключение focus ring проблему не решает.

Предлагаемая политика для этого конкретного диалога: разрешить закрыть окно, явно назвать действие «Закрыть» и объяснить, что построение продолжится. Операция и single-flight guard живут в странице; там остаётся статус процесса. Пока запрос не завершён, повторная генерация недоступна. Закрытие не является отменой серверного действия. Если окно остаётся открытым, ошибка показывается по T-DIALOG-ERROR-001; если закрыто — в видимой странице.

Альтернатива: временно недоступное закрытие с честно disabled control, видимым progress и корректной фокусировкой panel. Тогда необходимо отдельно определить выход при зависшем запросе без ложного обещания отменить серверное действие. Это решение ещё не принято; нельзя выбирать его молча в реализации BUG-022.

Обе политики сохраняют disabled semantics/визуальный вид radio-cards во время запроса и выбранный алгоритм. Не применять выбранную политику автоматически к выдаче временного пароля, подтверждению результата или другим диалогам с отличающимися последствиями.

## Проверка

Контролируемые pending/503/lost-response/permission/status-change на synthetic tournament,390/1440 и клавиатура. Проверять местоположение Alert, focus, доступный recovery, количество POST и authoritative bracket/version. Отдельно page state после закрытия/возврата. Все проверки после GAP-012 recheck; source-only контрастная гипотеза F-CMP-SUP-003 сюда не включена.
