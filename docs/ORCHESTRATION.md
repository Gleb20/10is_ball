# Оркестрация разработки Tab-10

Scope: TECH-005. Это протокол распределения работы; требования, права,
верификация и статусы остаются в [AGENTS.md](../AGENTS.md) и
[WORKFLOW.md](WORKFLOW.md). Исходная схема из
[чата настройки](https://chatgpt.com/share/6aa5d686-1f78-83ed-bcc9-0ec578b29d85)
адаптирована к текущему рабочему дереву 2026-09-13.

## Выбор маршрута

Главный агент владеет результатом и окончательной приёмкой. Модель по умолчанию —
Astra High; явный выбор пользователя имеет приоритет. Запрет «Astra не пишет код»
не применяется: небольшую известную правку выгоднее завершить непосредственно.

| Ситуация | Маршрут |
|---|---|
| Небольшая известная правка, поиск или ответ | Главный агент напрямую, необходимые проверки по риску |
| Неясно, где находится поведение; карту можно исследовать независимо | Luna Medium explorer |
| Ограниченная содержательная реализация | Sol Medium implementer; главный агент параллельно уточняет acceptance, зависимости или интеграционные проверки |
| Независимая проверка существенной реализации | Terra High reviewer; главный агент параллельно проверяет evidence и критические участки |
| Подтверждённые массовые обновления документации | Luna Low recorder; небольшие записи делает главный агент |
| Security, транзакции, конкуренция, неоднозначная архитектура | Главный агент разбирает критическую цепочку лично; Sol реализует ограниченные части, отдельный reviewer проверяет результат |

Делегирование должно давать самостоятельный проверяемый результат и полезную
работу для главного агента в это же время. Не запускайте обязательный конвейер
из всех ролей, повторную разведку известных файлов или агента ради одной записи.
При отсутствии полезной независимой работы выполняйте этап непосредственно.
Для существенной реализации независимое ревью предпочтительно; если оно
недоступно, главный агент выполняет отдельный review pass и явно отмечает,
что независимой проверки не было. Это не отменяет обязательные project gates.

Профили находятся в [.codex/agents](../.codex/agents/), настройки — в
[.codex/config.toml](../.codex/config.toml), точка входа —
[orchestrate-development](../.agents/skills/orchestrate-development/SKILL.md).
Используйте минимально достаточное число агентов: обычно один, до трёх дочерних
одновременно плюс главный. Реальный лимит инструмента может быть ниже.
Дочерние агенты не создают своих агентов.

## Контекст и work order

До назначения проверьте актуальные требования, относящийся к задаче техдолг и
открытые решения. Снимите `git status`, HEAD и исходные байты изменяемых файлов,
включая relevant untracked files. В dirty tree сравнение только с HEAD включает
чужую работу: review должен использовать разницу с началом конкретной задачи.
Храните scoped snapshot и patch в disposable каталоге вне Git; не копируйте
secret-bearing файлы. До записи снова сверяйте baseline; при чужом изменении
перечитайте его и согласуйте владение с главным агентом.

Передавайте минимум необходимого контекста и ссылки на исходные файлы, а не весь
чат. Для model override используйте новый контекст, если полный fork наследует
модель родителя и не поддерживает override. Шаблон задания:

```text
WORK ORDER: canonical backlog ID / short subtask label
GOAL: один наблюдаемый результат
BASELINE: workspace + HEAD + scoped snapshot/patch identity
SOURCES: applicable AGENTS, REQ/AT/ADR and relevant file paths
WRITE SCOPE: exact paths owned by this worker; forbidden paths
DEPENDENCIES: ready inputs/contracts; what must finish first
ACCEPTANCE: observable outcomes, including relevant negative cases
VERIFY: exact checks, disposable resources, required evidence
AUTHORIZATION: scope already granted; actions still outside it
RETURN: status, changed paths, evidence paths, checks/results/skips, risks
```

Не выдавайте worker новый backlog ID на каждую внутреннюю подзадачу. Если scope
нужно расширить, worker сообщает главному агенту. Главный сам решает технические
уточнения внутри уже разрешённой задачи; пользователя спрашивает только о
существенно меняющем результат решении или отсутствующем разрешении.

## Параллельность и интеграция

У каждого изменяемого файла один writer, включая самого главного агента.
Назначение действует до отчёта о завершении/остановке; отсутствие сообщений или
таймаут не освобождают владение. Before reassignment, stop the old writer and
inspect its partial changes. Главный агент ведёт короткий список owners и
зависимостей в текущем плане; отдельная система очередей не нужна.

Разные файлы не означают независимость. API и UI можно разрабатывать параллельно
только после фиксации общего контракта. Schema/migration, lockfile, общие типы,
канонические журналы, тестовая БД, порты и generated outputs требуют отдельного
владения или последовательной работы. Общий build/test запускает один владелец;
изолированные проверки допускаются на разных disposable ресурсах.

После остановки writers главный агент фиксирует состав task delta и integration
checks. Reviewer получает этот снимок и acceptance, а не только отчёт автора.
Новые изменения поведения/контракта после review требуют повторной проверки
затронутой области. Чистые изменения docs требуют проверки ссылок/согласованности.
Повторять неизменившиеся успешные проверки без причины не нужно.

## Приёмка, исправления и остановка

Worker возвращает READY_FOR_REVIEW, PARTIAL или BLOCKED. Reviewer возвращает
PASS, REWORK или INCOMPLETE. Это промежуточные отчёты, а не новые backlog statuses.
Главный агент сопоставляет acceptance с фактическими результатами, читает
критические участки и устраняет blocking findings до принятия реализации.

После двух неудачных циклов исправления одной причины прекратите идентичные
повторы: главный агент меняет гипотезу, сужает задачу, повышает effort в рамках
поддерживаемых моделей либо берёт проблему сам. Это не повод прекращать всю
разрешённую работу. При внешнем блокере выполните независимые части и точно
назовите недостающий факт/доступ. Не повторяйте неизвестно завершившуюся внешнюю
мутацию без проверки состояния.

Последовательность завершения: implementation evidence → review → проверка
интеграции главным агентом → canonical docs → проверка итогового delta → handoff.
Recorder получает только проверенные факты и разрешённый backlog status.
Окончательная приёмка происходит после документации. `verified_local` не означает
`verified_prod`; отсутствие production scope фиксируется явно по WORKFLOW.
Глобальная память Codex обновляется только по отдельному прямому запросу
пользователя, а не автоматически после acceptance.

В handoff укажите результат, точные проверки и skips, ограничения ревью и
следующий необходимый шаг. При прерывании сохраните owners, partial delta и
невыполненные проверки в существующем плане/backlog, не помечайте работу принятой.

## Совместимость и измерение эффективности

Формат сверен с [OpenAI Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents).
TOML profiles — defaults, а не изоляция файлов или гарантия поведения. Runtime
может переопределить sandbox; read-only роль обязана также избегать внешних
мутаций. Конфигурация не меняет approval policy, MCP, credentials или deploy.

Сначала проверьте доступные инструменты текущей сессии. Если custom agent selector
есть, используйте имя профиля. Если доступны только task/model/effort, прочитайте
соответствующий профиль, передайте его инструкции вместе с work order и задайте
явные model/effort. Не передавайте несуществующий `agent_type`. Если требуемая
модель/делегирование недоступны, сообщите это и выполняйте работу главным агентом
с теми же gates; не подменяйте модель молча и не запускайте внешние threads/CLI
как обход ограничения. Изменение файлов не перенастраивает уже работающий поток.

Для проверки установки используйте TOML parser, schema/config loader установленного
Codex, skill validator и `pnpm run audit:docs`. Проверка discovery и запуска
моделей — отдельный runtime smoke; статическая проверка их не доказывает.
Для smoke используйте новую сессию с корнем Tab-10 и bounded read-only задачей,
проверьте фактические модели/effort и возвращённые результаты. Не меняйте project
trust или разрешения автоматически, если конфигурация отключена средой.

Стоимость API-токенов не является мерой списания подписки Codex. Пока нет
сопоставимых запусков, экономия — гипотеза. Для нескольких похожих задач
сравнивайте доступные usage, длительность, число агентов и rework при одинаковых
acceptance gates. Если usage недоступен, оставьте его неизвестным. Калибруйте
маршрут по данным, не обещайте проценты экономии и не снижайте качество ради них.

Откат: восстановите только task delta из исходного scoped snapshot, предварительно
сверив, что затронутые файлы не получили новых чужих правок. Новые файлы пакета
удаляйте только при совпадении с принятой версией; не используйте reset/clean
для всего дерева. Затем повторите config/skill/docs checks.
