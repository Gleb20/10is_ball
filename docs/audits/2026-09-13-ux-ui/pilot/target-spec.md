# Целевая структура пилота

Статус: предложение для реализации после синтеза; приложение не изменено. Стили, палитра, шрифты и общий визуальный характер сохраняются. [Схемы desktop/mobile](wireframes.html) имеют порядковые аннотации; это структура, не новый дизайн.

## T-PILOT-CREATE — сначала состав, затем проверка правил

Вход остаётся `/matches/new`. Сохраняется весь существующий submit/validation/lifecycle. Форма не сохраняется после ухода (MATCH-015). До: [390](evidence/p03-create-top-390.png), [desktop](evidence/p27-keyboard-create-1440.png), [пустые suggestions](evidence/p29-a-boris-active-1440.png). После: wireframes, схемы 1–2.

Порядок блоков:
1. Заголовок «Новый матч». Переключатель «Формат»: 1×1 / 2×2. «Создатель играет» остаётся явной опцией с текущими defaults (manual=false; purposeful challenge/revenge=true).
2. «Состав»: отдельные группы «Сторона A» и «Сторона B», равные по виду. В каждой одно/два игровых места по формату; пользователь/гость и необходимые guest fields остаются внутри своего места. Быстрые варианты команд, недавних и частых соперников рядом с составом; показывать группу только при непустом фактическом наборе. Не добавлять пустой контейнер. Все фильтры active/distinct/busy и точные ID сохраняются.
3. Всегда видимая краткая сводка текущих правил: «До 11 · сухая 5:0 · первая подача вручную». Кнопка «Изменить правила» раскрывает inline region с отдельными видимыми labels для очков, mercy/порога и способа первого подающего. Значения всегда отражаются в сводке; отдельного сохранения нет, общий submit использует актуальное состояние. Нельзя скрывать отличные от defaults правила без сводки. Ошибка поля автоматически раскрывает блок и переводит focus к первому ошибочному полю.
4. Кнопка disclosure «Название, судья и приглашения» раскрывает текущие title/judge/invite controls. Под кнопкой всегда сводка: фактическое название; судья — не выбран/имя; приглашения — выключены/включены. Если prefill включает приглашения, соответствующее состояние видно до раскрытия. Опция приглашений не становится условием создания/старта. Полный каталог/поиск судьи остаётся доступен.
5. «Создать матч» и вторичная «Отмена» после формы. Sticky CTA не вводится этой задачей. Вся форма прокручивается с существующим резервом под BottomNav; клавиатура не приводит к клику сквозь неё.

390/360: одна колонка, текущие внешние 16px, внутренние токены spacing; одинаковые горизонтальные границы двух сторон/сводок/actions. 1440: существующий max-width shell сохраняется; две стороны на отдельных строках с одинаковыми field widths, без новой широкой dashboard-сетки. Никакого обязательства уместить 2×2 полностью в первый viewport. На 390×844 в исходном положении видны заголовок, формат и первое игровое место; редкие настройки больше не предшествуют ему.

Клавиатура следует визуальному порядку. Disclosure — обычный button с aria-expanded/aria-controls; регион именован. После раскрытия focus остаётся на кнопке, следующий Tab попадает внутрь. После сворачивания сфокусированного region focus возвращается trigger. Не использовать Dialog и не удалять focus indicator. Ошибки directory/empty/retry различимы по общему контракту; связанные BUG-018/019/023 и состояния directory могут быть поставлены раньше этой задачи.

Pending общий submit: показывать отправленную неизменяемую конфигурацию, блокировать повтор и управляющие ею поля до определённого результата; не менять payload задним числом. При известной ошибке сохранять введённые данные, показывать ошибку рядом с действием/полем. Не добавлять optimistic создание или автоматический повтор неизвестного результата. Это требует согласования с общим pending contract, а не локального второго решения.

Сохраняются: custom points, mercy threshold/off, manual/random/rally, 1×1/2×2, creator inclusion, registered/guest/team/recent/frequent, title, optional judge, voluntary invites, challenge/revenge prefill, cancellation/back/validation. API/types/data: none. Доступные функции MATCH-004 сначала сверить с текущим createOptions, не изобретать отсутствующие данные.

## T-PILOT-DETAIL — следующий шаг соответствует роли и состоянию

Предложение для MATCH/JUDGE/RESULTS; до синтеза не ready. До: [waiting](evidence/p07-match-waiting-390.png), [finished operator](evidence/p32-result-1440.png).

- Waiting creator, нет чужого активного judge/reservation: основной «Начать и вести счёт» открывает существующий judge route с существующим acquire и выбором first serve. Не объединять create+start в новую транзакцию.
- Waiting creator, другой judge уже активен/зарезервирован: сохранить доступный существующий «Начать матч» с его текущими проверками; не захватывать судейство. Состояние «Счёт ведёт …» явно. Детальная таблица reservation/creator/judge и ошибки acquire уточняется JUDGE.
- In_progress: основной «Продолжить ведение» только при доступе своей сессии; иначе «Открыть счёт». Активный owner известен явно. Нельзя заменять guards видимостью кнопки.
- Finished: итог, стороны, победитель и причина выше журнала; основной «Новая игра» → пустой manual `/matches/new`. Это не копирование состава и не реванш. Существующий доступный «Создать реванш» остаётся отдельным действием с исходными правилами. История, лог, void сохраняются. Void в раскрываемых «Действиях с результатом», только существующим субъектам, с прежним подтверждением и audit.
- Журнал очков ниже текущих действий; пустой журнал не занимает отдельную большую карточку до первого очка. Техническая коррекция не маскируется под игровое очко.

## T-PILOT-JUDGE — понятное управление текущей игрой

Предложение JUDGE; ограничения размеров/landscape дополнительно проверяет пакет. +1 и текущая подача сохраняют сильный приоритет. «Undo» → «Отменить очко», с существующим aria-name. «Ещё» раскрывает коррекцию, перестановку на экране, освобождение и передачу. Названия «Передать на другое устройство» и «Завершить ведение и выйти» заменяют термин «слот» без изменения протокола. Краткая помощь различает: один телефон — просто передать телефон, записи остаются аккаунту; другое устройство — выбрать получателя, тот принимает ведение в своём аккаунте. Без обязательной идентификации физического человека. Не убирать объяснение отмены; поместить развёрнутое в помощь, краткое оставить доступным.

## T-PILOT-HOME — приоритет начала и текущего действия

Экспертная гипотеза для AUTH: greeting → begin/resume → active games + actionable notifications → compact personal stats → recent events/ranking/profile. Все HOME-001–006 функции сохранены; конкретный порядок групп/notification count уточняется AUTH и интервью. Пока не менять принятую HOME структуру в требованиях как якобы реализованную.

## Не разрешено этим предложением

Новый clone match, сохранение черновика между визитами, изменение правил/права старта, доступ к чужому активному матчу, автоматическая запись счёта/инвайты, широкие admin права, переоформление бренда. Неподтверждённые предположения о пользователях не становятся требованиями.


## Уточнение после AUTH прохода — 2026-09-14

Фраза о несохранении формы относится к обычному уходу/размонтированию по MATCH-015. Существующее восстановление после runtime401 сохраняется: безопасный in-memory draft остаётся смонтированным, hidden/inert; тот же actor после reauth возвращается к нему, другой actor получает новое чистое дерево. Отклонённая mutation не повторяется. Основание: AUTH-006, AT-AUTH-009, UX_FLOWS §3.1. Это уточнение не вводит localStorage/server drafts и должно войти в приёмку GAP-013. Прежний frozen pilot-review описывает предыдущие bytes; уточнение подлежит следующему consistency review.
