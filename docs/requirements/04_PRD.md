# PRD — Tab-10 MVP

## Принятый целевой overlay D40 — 2026-10-03

[D40](../DECISIONS.md) закрывает продуктовые развилки Q-UX-001..004 и
Q-UX-006..010; Q-UX-005 уже закрыт D38. Более ранние readiness-ограничения по
этим вопросам ниже описывают исторический объём этапов до принятия D40 и не
блокируют согласованную новую реализацию. Они не являются второй целевой моделью.

- GAP-013/GAP-023: редактируемый судейский экран → «Начать» → выбор подачи →
  атомарный запуск → счёт; правила в шторке до старта, затем контекстное меню в
  том же углу. Нет серверного draft до отправки launch и нет промежуточной карточки.
- GAP-032/GAP-017: редактируемый повтор обычного состава/правил; достоверная
  история аккаунтов ведущих; прежнее подтверждённое аннулирование без 10-секундного Undo.
- GAP-013/GAP-019: переиспользуемые гости без автоматического объединения;
  GAP-019: плановая будущая дата без автоматического старта.
- GAP-025: необязательный готовый аватар команды. GAP-028: active-admin lookup
  по точному ID только минимальных полей и разрешённой аварийной операции.
- BUG-022: закрываемое окно генерации, процесс на странице, защита повторов и
  честное восстановление неизвестного исхода. D35 и права не ослабляются.

Принятие решения не закрывает implementation/browser/PostgreSQL/release gates.
Физические iPhone-наблюдения не заменяются эмуляцией. D37 и Q-UX-011 сохраняются.

Статус: Target requirements; фактическое покрытие — в [`../CAPABILITY_MATRIX.md`](../CAPABILITY_MATRIX.md)
Подход: TDD mandatory

## 1. Scope

Документ описывает автономный закрытый продукт с локальными аккаунтами и локальной теннисной админкой.

### UI-001 Статус и иконка сохраняют свой смысл на разных экранах

Статус матча, турнира, судейского слота, команды, уведомления или аккаунта
представляется как информация, если сам элемент не выполняет действие. Его
текст и доступное имя объясняют значение без угадывания цвета или иконки;
интерактивный элемент имеет отдельную роль, доступное имя и focus state.
Selected/active control не выдаётся за persisted domain status, а pending/error
не скрывают доступное продолжение. Общая семантика применима к Home, match/judge,
tournament/bracket, history, notifications, team и admin в пределах видимости
D17/D37. Точный набор chip/icon семейств и визуальный target фиксируются в
GAP-034 до межэкранной реализации; текущий опубликованный UI остаётся baseline,
без смены бренда и доменных прав.

## 2. Акторы и права

### Системные роли
- `admin` — все возможности `user` плюс управление локальными аккаунтами.
- `user` — все спортивные возможности.

### Контекстные права
- организатор матча;
- организатор турнира;
- текущий судья;
- капитан команды;
- участник события.

### Общие правила
- Любой активный `user` может создать матч, турнир или команду.
- Только капитан приглашает в команду, редактирует её и исключает участников.
- Любой участник команды может без подтверждения включить другого текущего участника этой команды в матч или турнир.
- `admin` не получает права напрямую редактировать завершённый спортивный
  результат. Активный `admin` или создатель матча может только выполнить
  auditable soft-invalidation `void` по MATCH-016; исходные факты не
  переписываются и не удаляются.

## 3. AUTH — локальный вход

### AUTH-001 Закрытый доступ
Без активной сессии доступны только экран входа. Все продуктовые URL ведут на логин.

### AUTH-002 Создание аккаунта
Самостоятельной регистрации нет. Аккаунт создаёт администратор.

Обязательные поля:
- имя;
- фамилия;
- email.

Опциональные:
- дата рождения;
- организация;
- должность.

### AUTH-003 Временный пароль
При создании/сбросе аккаунта администратор получает случайный временный пароль, отображаемый один раз. При первом входе пользователь обязан задать новый пароль.

Повторное чтение результата сброса никогда не возвращает открытый пароль.
Полученный ответ хранится клиентом только в памяти текущей вкладки до Close;
Copy не уничтожает показ. Reload, logout, смена actor или потеря роли уничтожают
его. Для self-reset ожидаемый автоматический `401` может сохранить только точно
связанный ответ собственной операции до явного закрытия.

До успешной смены пароля ограниченная сессия не даёт читать или изменять
продуктовые данные. Среди защищённых API доступны только получение текущего auth
context, logout и установка первого постоянного пароля; точные method+path заданы
в `08_API_SPEC.md`.
На экране обязательной смены действие «Выйти» завершает только текущую
ограниченную серверную сессию. После успешного выхода либо уже истёкшей сессии
открывается вход; известная ошибка выхода сохраняет введённые значения и
допускает только явный повтор. Неизвестный сетевой исход не объявляется
подтверждённым выходом.

### AUTH-004 Пароль
Новый пароль:
- не короче 10 символов;
- содержит цифру;
- строчную латинскую букву;
- заглавную латинскую букву;
- допустимый спецсимвол.

Поле скрыто, имеет действие «показать». Генератор пароля разрешён.
Раскрытие встроено в каждое поле пароля, доступно с клавиатуры и не отправляет
форму; значение и узел ввода сохраняются при переключении. Ошибка несовпадения
связана с обоими полями, причины политики показаны понятными действиями без
внутренних кодов. Каждая явная неуспешная отправка, включая повтор с тем же
текстом ошибки, возвращает фокус одному сообщению; исправление поля не
перехватывает его повторно.

### AUTH-005 Обычный вход
Email + пароль. Заблокированный пользователь не входит. Успешный ответ входа
определяет следующий экран: обязательная смена пароля, незавершённое обучение,
затем безопасный контекст возврата. Повторное чтение аккаунта не является
условием завершения успешного входа (BUG-042).

### AUTH-006 Сессия
- срок сессии — 7 дней с момента последней успешной активности;
- несколько обычных сессий пользователя разрешены;
- logout завершает текущую сессию;
- смена пароля сохраняет текущую сессию и завершает остальные.

### AUTH-007 Восстановление
Self-service recovery и email-отправка не входят в MVP. Администратор сбрасывает пароль и выдаёт новый временный пароль.

### AUTH-008 Активные сессии
В профиле отображаются активные сессии пользователя; можно завершить другую сессию.

### TDD gate
До реализации написать тесты `AT-AUTH-001..012`.

## 4. ADM — теннисная админка

### ADM-001 Доступ
Админка доступна только роли `admin`.

### ADM-002 Список пользователей
Показывает имя, email, роль, статус, дату создания, дату последнего входа. Есть поиск по имени/email и фильтр статуса.
Поиск, фильтр, число результатов и ссылки на аккаунты предшествуют вторичному
созданию. Форма создания по умолчанию закрыта и существует в одном экземпляре.

### ADM-003 Создание
Администратор создаёт пользователя, выбирает `user` или `admin`, получает временный пароль.

### ADM-004 Редактирование
Можно менять имя, фамилию, дату рождения, организацию, должность и роль. Email в UI MVP не меняется.

### ADM-005 Блокировка
Блокировка немедленно завершает все сессии. Пользователь исчезает из выбора для новых событий, но остаётся в истории.

### ADM-006 Разблокировка
Возвращает возможность входа и участия в новых событиях.

### ADM-007 Сброс пароля
Создаёт новый временный пароль, завершает все сессии и требует смены пароля при следующем входе.

Каждая попытка имеет UUID request id и сравнивается с последним применённым
admin-reset target. Неизвестный сетевой исход сверяется exact receipt GET без
повторной выдачи секрета. Новый replacement допускается только после отдельного
подтверждения и с новым request id; старый legacy POST без ключа отклоняется до
мутаций. Receipt, пароль, отзыв сессий, issue, audit и notification атомарны.

### ADM-008 Аудит
Фиксируются создание, редактирование, блокировка, разблокировка, смена роли и сброс пароля.
Карточка аккаунта показывает только разрешённые данные пользователя и безопасную
проекцию его аудита: время, разрешённое действие, текущую подпись исполнителя и
названия изменённых полей. Старые/новые значения, произвольная metadata,
пароли, токены, сессии и внутренние исходы не выдаются.

### TDD gate
До реализации написать тесты `AT-ADM-001..010`.

## 5. HOME — главная

### HOME-007 Глобальный вход и навигация (D36)
Главная `/` — единственный глобальный вход без bottom tabs и общего меню.
Внутри задания доступны понятные Back и Home; контекст возврата сохраняет
источник, фильтры и позицию при переходах сетка → матч → та же сетка и история →
детали → те же фильтры. Reload, deep link, first-password, повторный вход,
403/404 и выход из судейства имеют безопасный путь к Home без ложного обещания
освобождения judge slot. Все прежние разрешённые разделы остаются обнаружимыми.

### HOME-001 Состав
- компактная шапка: аватар, имя, фамилия, ранг, матчи, победы, поражения;
- прямые CTA «Начать матч» и «Провести турнир»;
- активные события;
- последние 5 завершённых матчей/турниров с переключением «Все / Только мои»;
- топ-3 рейтинга;
- вход в уведомления;
- вход в профиль.

### HOME-002 Hero
В шапке остаются сыгранные матчи, победы и поражения. Win rate, средние очки и
другие вторичные показатели доступны в профиле. CTA «Реванш» временно скрыт
по D37; сохранённые данные соперника не удаляются.

### HOME-003 Последние события
Краткая карточка обычного завершённого матча ставит стороны и счёт в основной
ряд, длительность — третьим уровнем. Победившая сторона отмечена у своего имени
по серверному `winnerSide`, с доступным текстом; совпадающие имена не служат
основанием для выбора победителя. Повторную строку с именем победителя и обычный
статус «Завершён» не показываем. Если сторона победителя неизвестна, знак не
добавляется. Остановленный, отменённый и аннулированный матч сохраняет краткое
обозначение особого исхода. Формат, судья и остальные сведения доступны в
деталях результата по переходу. Карточка турнира показывает топ-3, длительность
и отметку участия или судейства без изменения турнирных мест.

### HOME-004 Активные события
Можно одновременно показывать турнир и один отдельный матч. Пользователь не может играть два активных матча одновременно.
Отбор актуального дела учитывает роль игрока, текущего судьи и организатора в
пределах действующих прав видимости; ближайшее действие показывается до истории.
Все собственные текущие дела доступны без скрытого отсечения; первые два видны
сразу, остальные раскрываются через «Ещё N текущих дел». Идущая игра, в которой
пользователь играет или сейчас судит, стоит выше более нового ожидающего матча.
«Только мои» отбирает завершённые события с участием пользователя **игроком**
до ограничения последними пятью; одно лишь судейство не считается участием.
Пустой блок не выдаёт приглашённые турниры за все активные события.
Home получает актуальные данные фоновым обновлением; постоянная ручная кнопка
«Обновить» не занимает экран. После ошибки загрузки доступен явный Retry.
Пока первый ответ Home загружается или закончился ошибкой, входы в историю и
рейтинг остаются видимыми вместе с прочими разрешёнными разделами; неизвестные
метрики не выдаются за нули.

### HOME-005 Рейтинг
По умолчанию топ-3 за всё время; быстрый переключатель «за всё время / за месяц».

### HOME-006 Empty states
Для отсутствующих матчей, рейтинга, соперника и активных событий показывается объяснение и релевантный CTA.

## 6. PROFILE — профиль

### PROFILE-001 Свой профиль
Показывает:
- имя, фамилию, email, организацию, должность, дату рождения, аватар;
- матчи, победы, поражения, win rate, средние очки;
- турниры, победы в турнирах, созданные турниры;
- матчи в роли судьи;
- текущий общий рейтинг;
- места в текущих командах.

### PROFILE-002 Интересные факты
- самая долгая игра;
- лучший победный счёт;
- частый соперник;
- принципиальный соперник.

Частый и принципиальный соперник считаются только среди зарегистрированных активных или исторических пользователей, не гостей.

### PROFILE-003 Редактирование
Можно изменить локальные поля профиля. Email и аватар не меняются (D10).
Клиентская проверка повторяет границы серверного контракта: имя и фамилия после
удаления пробелов по краям содержат 1–100 символов, организация и должность — не
более 200, дата рождения — существующая дата `YYYY-MM-DD` с положительным годом.
Ошибка связана с конкретным полем и сохраняет черновик. При сетевом или `5xx`
исходе сохранение считается неизвестным: автоматический повтор `PATCH` запрещён,
а явное «Обновить данные» выполняет только `GET` и не объявляет исход подтверждённым.

### PROFILE-004 Аватар
По принятому D10 при создании user/guest один раз назначается один из десяти
статических пресетов `avatar_1`…`avatar_10`; повторы допустимы. Редактирование,
загрузка и повторная генерация аватара вне текущего этапа. Профиль показывает
назначенный аватар без элементов редактирования. D10 supersedes исходное
требование upload/regenerate.

### PROFILE-005 Чужая карточка
Доступна всем активным пользователям и показывает:
- имя, фамилию, аватар, организацию, должность;
- матчи, победы, поражения, win rate, средние очки;
- сыгранные турниры, победы в турнирах, созданные турниры;
- матчи в роли судьи;
- место в рейтинге;
- CTA «Бросить вызов».

Пока действует D37, CTA «Бросить вызов» в этой карточке скрыт; данные карточки
и доступ к истории сохраняются.

Дата рождения и email не показываются.

### PROFILE-006 Актуальные данные в истории
После изменения имени или аватара новые данные отображаются и в исторических карточках.

## 7. RANK — рейтинг

### RANK-001 Формула
Рейтинг строится по абсолютному количеству побед.

Порядок:
1. `wins DESC`;
2. `win_rate DESC`;
3. `matches_played DESC`;
4. `created_at DESC` — позже созданный аккаунт выше.

### RANK-002 Периоды
- all time — по умолчанию;
- текущая календарная неделя;
- текущий календарный месяц.

Границы недели/месяца и пользовательское отображение определяются в
`Europe/Moscow`. Абсолютные timestamps хранятся/передаются в UTC (ADR D20).

### RANK-003 Матчи с гостями
Учитываются в рейтинге зарегистрированного игрока. Гость в рейтинг не попадает.

### RANK-004 Командный рейтинг
Сравниваются текущие участники команды по их общим показателям.

### RANK-005 Карточка игрока
Нажатие открывает публичную карточку.

## 8. HISTORY — история

### HISTORY-001 Состав
Единый список матчей и турниров пользователя.
Строка матча показывает обе игровые стороны из текущего имени или сохранённого
guest snapshot; для турнира эти поля отсутствуют. Это объясняет совпадение поиска
и не раскрывает идентификаторы или email участников.

### HISTORY-002 Фильтры
- период;
- роль игрок/судья;
- победа/поражение;
- матч/турнир;
- поиск по фамилии любого участника матча, в том числе когда текущий пользователь
  был только оператором, или названию турнира.

### HISTORY-003 Видимость
- активное событие видят только его организатор, участники и **текущий активный**
  судья;
- завершённое событие видят все активные (`status != blocked`) пользователи клуба;
- tutorial-события не попадают в общую историю и списки.

### HISTORY-004 Неактивные аккаунты
Заблокированный пользователь скрыт из новых списков и рейтинга, но остаётся в исторических событиях.

## 9. MATCH — создание и жизненный цикл матча

### MATCH-001 Создание
Создатель является владельцем матча, но может быть оператором у стола и не
занимать игровое место. В ручном flow опция «Создатель играет» по умолчанию
выключена. Название по умолчанию: `Матч {дата и время}`. Название меняется только
до старта.
Пока отправка создания ожидает ответ, видимые поля отправленного состава,
названия, формата и правил недоступны для изменения. При известном отказе
введённые значения сохраняются для исправления и явной повторной отправки.
По D40 подготовка выглядит как судейский экран с двумя сторонами и выбором
игроков. Правила и название доступны через шторку до явного «Начать». Это
действие переводит к выбору первой подачи; её выбор запускает atomic launch,
после подтверждения которого открывается счёт. Дополнительной карточки старта нет.

### MATCH-002 Формат
- `1v1`;
- `2v2` только для обычного матча.

### MATCH-003 Участники
- зарегистрированные пользователи;
- участники общей команды без подтверждения;
- одноразовые гости: имя + фамилия.

Существующие одноразовые гости сохраняются. По D40 отдельно доступна повторно
используемая guest identity с историей; одинаковые имена не объединяются,
старые snapshots не переписываются и автоматически не привязываются.
Зарегистрированный участник должен существовать и быть активным; один user не
может занимать несколько мест или играть против себя. Состав обязан точно
соответствовать формату; владелец и игровые участники — независимые роли.
Выбор зарегистрированного игрока не создаёт приглашение автоматически.
«Пригласить выбранных игроков» — отдельная, по умолчанию выключенная опция.
Пока действует D37, этот UI и все игровые приглашения скрыты, а ручное создание
не отправляет их. Переиспользуемый гость выбирается явно; исправление имени разрешено создателю
либо active admin и не меняет исторические подписи.

### MATCH-004 Быстрый выбор
Селектор показывает:
- поиск по имени/фамилии;
- мои команды;
- недавние соперники;
- частые соперники.

### MATCH-005 Правила
Настройка до серверного старта (локальная кнопка «Начать» по D40 лишь открывает
выбор подачи и ещё не выполняет серверный старт):
- очки до победы: 11, 21 или своё значение;
- сухая победа: включена/выключена и порог;
- определение первого подающего: random/manual/rally в следующем экранном шаге,
  после локального «Начать», до отправки atomic launch;
- формат 1v1/2v2.

По D38 последнее выбранное значение `11`/`21`/custom сохраняется только пока
открыта текущая форма, включая повторное открытие цифровой панели. Оно не
переносится в другую форму, маршрут, сессию, устройство или пользователя; смена
1v1/2v2 сама по себе его не заменяет.

По D40 default mercy threshold равен max(1, floor((N−1)/2)); ручной выбор
сохраняется, исторические настройки не пересчитываются.
После старта правила неизменны.

### MATCH-006 Победа
Обычная победа: достигнут лимит и отрыв не менее 2. При разнице 1 игра продолжается; после достижения порога подача переходит после каждого очка.

Сухая победа: при включённом правиле матч завершается при достижении настроенного отрыва.

### MATCH-007 Подача
До deuce смена после двух подач, после deuce — после каждой. В 2v2 система знает текущего подающего внутри пары и поддерживает упрощённую ротацию и смену сторон.

### MATCH-008 Старт
Матч может стартовать только его создателем/организатором и только при валидном
составе:
- 1v1 — две стороны по одному игроку;
- 2v2 — две стороны по два игрока.

Pending/declined player или judge invitations не блокируют старт. Успешный старт
атомарно закрывает все ещё pending invitations как `cancelled/match_started` и
помечает их notifications прочитанными.
Только для уже существующих waiting матчей и турнирных матчей сохраняется
legacy start/setup API: в этой двухшаговой подготовке видимые выбор первой подачи, сторон и действия
остаются неизменными до ответа на оба шага. Подтверждённый старт не отправляется
повторно при явной коррекции setup после известного отказа. Неизвестный исход
любого шага не разрешает повторную мутацию на основании одного раннего чтения.

Для нового обычного матча D40 launch атомарно создаёт матч, назначает текущую
auth session судьёй, задаёт подачу и стартует. До отправки нет серверного draft.
Повтор ключа не создаёт второй матч; unknown outcome требует reconciliation.
Receipt не заменяет свежий GET и проверку текущего владельца судейской сессии.

### MATCH-009 Конкурентность игрока
Пользователь не может одновременно играть в двух активных матчах. Участие в турнире как сущности не блокирует отдельный матч, если текущий турнирный матч пользователя не активен.

### MATCH-010 Завершение
После победного очка время останавливается, но результат становится окончательным только после подтверждения судьёй. До подтверждения можно отменить окончание и продолжить. Подтверждение атомарно фиксирует result/event version, статистику, освобождение judge session и, для tournament match, переход сетки; повтор того же подтверждения тем же judge session не применяет эффекты второй раз.

### MATCH-011 Read-only
После подтверждения результат, правила и логи недоступны для редактирования.

### MATCH-012 Остановка
Досрочно остановить матч может только его создатель/организатор или текущий
активный судья. Он выбирает:
- причину из трёх пресетов или свой текст;
- победителя.

Остановленный матч учитывается в истории, статистике и рейтинге. Terminal result,
статистика, judge release и tournament advancement коммитятся одной транзакцией.

### MATCH-013 Неявка
Организатор или текущий судья вручную фиксирует неявку. Вторая сторона получает победу; причина видна в деталях.

### MATCH-014 Быстрый вызов
«Бросить вызов» и «Реванш» открывают предзаполненный flow создания матча, где
инициатор играет, а приглашение выбранным игрокам включено как намеренное
действие. Можно подтвердить правила по умолчанию или изменить их.
Пока действует D37, Challenge/Revenge не доступны в UI, включая старые prefill
ссылки и подсказки. Этот контракт сохраняется для последующего решения.

### MATCH-015 Черновики
Незавершённый flow создания не сохраняется.

### MATCH-016 Void ошибочно завершённого результата

Ошибочно завершённый матч не удаляется и не переписывается. Он переводится в
статус `voided` с обязательным immutable audit trail, компенсацией уже применённой
статистики. Для tournament match прежнее продвижение winner/loser сохраняется как
исторический факт: bracket JSON/version, downstream matches/results/stats и
notifications не меняются; replacement/cascade/repair flow не создаётся (D33).
Hard delete завершённого
спортивного результата запрещён. Инициировать void может только активный `admin`
или создатель матча (`created_by_user_id`); второй approver не нужен, причина
опциональна. До отправки запроса UI явно подтверждает soft-invalidation и влияние
на статистику. Повторный void идемпотентен, а unauthorized/stale запрос не меняет
ни матч, ни статистику, ни зависимые сущности (ADR D19/D24/D33).

### MATCH-017 Отмена standalone-матча

Standalone-матч в `waiting`, `in_progress` или `pending_confirmation` может
отменить только активный `admin` или создатель матча. Участник и текущий судья не
получают это право автоматически. Причина опциональна. Cancel переводит матч в
`cancelled` без победителя и статистики, освобождает judge session и занятость
игроков; это отдельное действие, не early stop из MATCH-012. UI требует явного
подтверждения с названием матча и последствиями, а сервер независимо проверяет
actor, состояние, версию и идемпотентность (ADR D23). Запрос содержит текущий
`expectedVersion` и UUID `Idempotency-Key`: повтор того же actor/match/key
возвращает уже зафиксированный outcome, а stale или конкурирующий новый key не
меняет match, judge session, статистику или event log.

## 10. JUDGE — судейство

### JUDGE-001 Один судья
У матча может быть только одна активная judge session.

### JUDGE-002 Допустимые судьи
Any active registered club user may acquire a free judge slot or accept a handover.
Match/tournament participation is not required (accepted D7). Blocked users cannot
acquire or accept. JUDGE-004 device and simultaneous-judge limits still apply.

### JUDGE-003 Захват
Первый допустимый пользователь, успешно захвативший свободный слот, становится судьёй.

### JUDGE-004 Устройство
Judge session привязана к `user_id + auth_session_id`. Один пользователь не может судить с двух устройств и не может судить два матча одновременно.

### JUDGE-005 Занятый слот
Другому пользователю показывается:
> Этот матч уже судит «Имя пользователя», два судьи у матча — дело к драке. Давай не будем.

### JUDGE-006 Release
Судья может освободить слот. Матч остаётся `in_progress` и показывает, что требуется судья.
Явный внутрисервисный Browser Back ждёт завершения уже отправленной операции и
очереди очков, затем выполняет один best-effort release и продолжает исходный
переход с его history state. Неизвестный исход не вызывает повтор начисления;
сохранённое восстановление остаётся доступным при возврате Forward. Если безопасно
сохранить восстановление нельзя либо открыто решение о коррекции/результате,
переход отменяется с объяснением. Отказ/таймаут освобождения не выдаётся за успех.
Перезагрузка, закрытие вкладки и уход в фон по-прежнему используют TTL.


### JUDGE-007 Handover
Судья может атомарно передать слот конкретному допустимому пользователю. До принятия/старта новой judge session слот зарезервирован за ним.

### JUDGE-008 Heartbeat
Клиент отправляет heartbeat. После заданного TTL без heartbeat judge session освобождается. Рекомендация: heartbeat 30 секунд, TTL 120 секунд.

### JUDGE-009 Начисление
Каждое очко отправляется на сервер с уникальным idempotency key и просмотренной
expected match version. До POST клиент сохраняет actor/match, сторону, ключ и
версию. После ошибки точное наличие известного ключа в полном authoritative GET
доказывает применение; отсутствие ключа само по себе не доказывает отказ.
Отправленные попытки и ещё не отправленная FIFO-очередь учитываются независимо.
После любой ошибки очередь продолжает работу только по явному решению судьи;
автоматически она продолжается лишь после обычного успешного ответа POST.
В режиме счёта вся карточка стороны является одной крупной зоной `+1`, доступной
мышью, клавиатурой и вспомогательным технологиям. Pointer move дальше порога и
`pointercancel` подавляют следующий синтетический click, чтобы завершение
прокрутки не начисляло очко; обычный tap/click и клавиатурная активация сохраняют
действующий versioned FIFO контракт.

### JUDGE-010 Undo
Undo откатывает последнее действующее очко и всё производное состояние: счёт, подачу, deuce, потенциальное завершение.

### JUDGE-011 Аварийная коррекция
Спрятана в дополнительном меню. Разрешена только активному судье до подтверждения результата. Коррекция оставляет технический audit trail.
Два поля счёта имеют различимые подписи, связанные с соответствующими полями;
ошибка в тёмной оболочке судьи остаётся читаемой.
Перед POST сохраняются неизменяемые абсолютные значения счёта, подающий,
expected version и raw UUID. Применение доказывает только полный GET с точным
`manual-correction:<UUID>` либо успешный ответ этой попытки. Неизвестный исход
не повторяется автоматически и не смешивается с редактируемым черновиком.

### JUDGE-012 Чистый пользовательский лог
В отображаемом логе остаются только действующие очки. Отменённые события сохраняются технически, но не показываются как часть чистой истории.

## 11. TOURNAMENT — турнир

### TOURNAMENT-001 Создание
Название по умолчанию: `Турнир {дата и время}`. Название меняется до старта.

Организатор до приглашения выбирает:
- участвует как игрок;
- только организует.

Также один раз при создании выбирается policy согласия зарегистрированных
участников: direct roster (по умолчанию) или required consent. Policy сохраняется
в турнире и после создания не меняется.
Пока действует D37, UI создаёт новые турниры только с
`requireParticipantConsent=false` и не показывает выбор consent или игровые
приглашения; существующие записи с иным policy не мигрируются автоматически.
Создание и pre-generation карточка показывают правила языком игрока: состояние
сетки проигравших, очки до победы, сухую победу и участие организатора. В
`collecting`/`needs_regeneration` порядок — правила, состав, затем действие с
сеткой; правила остаются авторитетно редактируемыми до старта.

### TOURNAMENT-002 Минимум/максимум
- минимум 3 игровых участника;
- максимум 64;
- организатор без участия не считается игроком.

Если игровых участников двое, создаётся обычный матч, а не турнир.

### TOURNAMENT-003 Форматы
- single elimination;
- double elimination с одним финальным матчем.

Round robin вне MVP.

### TOURNAMENT-004 Матчи
Только 1v1. Один набор правил применяется ко всем матчам турнира.

### TOURNAMENT-005 Сбор участников
Источники:
- приглашённые зарегистрированные пользователи;
- текущие участники команд;
- гости.

Быстрое приглашение зарегистрированного пользователя живёт 10 минут. Турнир не стартует автоматически.
Прямое добавление и удаление участника из roster выполняет организатор этого
турнира. Активный global admin может только увидеть минимальные title/status и
active-roster поля и вручную добавить зарегистрированного пользователя; это не
даёт ему приглашение, удаление, настройки, bracket или lifecycle права. В режиме
required consent, а для non-organizer admin всегда, ручное добавление требует
отдельного confirmation с именем игрока, турниром и последствиями. Гостей напрямую
добавляет только организатор. Принятие адресного приглашения и самостоятельный
выход участника остаются отдельными contextual actions.
Обычное прямое добавление организатором в `collecting` при
`requireParticipantConsent=false` выполняется по явной кнопке без второго
confirmation. `needs_regeneration`, required consent, scoped admin и готовая
сетка сохраняют свои confirmation и regeneration guards.
Для пары `турнир + пользователь` существует не более одного pending-приглашения
и одного active participant. Повтор invite пока приглашение pending возвращает
его же без второй карточки; после terminal state новый invite создаёт новую
запись. Invite, response и добавление participant фиксируются атомарно и
идемпотентно при retry/гонке. Ручное добавление сохраняет actor/source provenance
и audit; optional UUID `Idempotency-Key` делает точный retry no-op, а повтор ключа
с другим payload отклоняется.
Пока ручное включение ожидает ответ, выбранный зарегистрированный игрок остаётся
видимым и недоступным для изменения. Известный отказ сохраняет выбор для
исправления; результат успешного действия сверяется чтением состава.

### TOURNAMENT-006 Комната ожидания
Показывает статус сбора, подтверждённых/автоматически добавленных участников, ожидающие приглашения и CTA «Сгенерировать сетку» при 3+ игроках.

### TOURNAMENT-007 Генерация сетки
Только организатор соответствующего турнира запускает генерацию или
перегенерацию сетки. После нажатия:
- ordinary roster edit закрывается;
- pending приглашения становятся неактуальными;
- строится сетка;
- организатор может менять пары и bye-позиции.

До старта organizer или scoped active admin может отдельным подтверждённым
действием добавить зарегистрированного игрока: participant, stale invite closure,
audit и полная перегенерация составляют одну transaction. Существующий seed prefix
сохраняется, новые игроки добавляются в deterministic insertion order. Без
`confirmBracketRegeneration` нет записей.
Ошибка построения показывается в открытом окне вместе с выбранным алгоритмом.
Неизвестный исход не разрешает повторное построение в этом окне даже после
раннего чтения состояния или повторного открытия. Успех показывается после
подтверждённого ответа и актуального чтения сетки.
Если построение подтверждено, а чтение сетки не удалось, явная успешная проверка
актуальной сетки завершает обновление интерфейса; до неё повтор заблокирован.

### TOURNAMENT-008 Посев
Источник — рейтинг all time. Игроки без рейтинга и гости распределяются случайно среди несеяных.

### TOURNAMENT-009 Bye
Сетка допускает нечётный состав. Система назначает проходы автоматически; организатор может переставить участников до старта. Один игрок не должен получать больше одного bye за турнир, если это математически возможно.

### TOURNAMENT-010 Роспуск сетки
До старта организатор может распустить сетку и вернуться к сбору участников. Принятые участники сохраняются.

### TOURNAMENT-011 Выход до старта
Участник может выйти. Если сетка уже построена, она получает статус `needs_regeneration` и не может быть запущена до новой генерации.

### TOURNAMENT-012 Старт
Только организатор соответствующего турнира может нажать «Начать турнир» и
зафиксировать сетку. После старта нельзя добавлять участников, менять пары,
правила или формат. Перед первой записью старта система проверяет весь игровой
roster, включая участников с bye: зарегистрированный organizer/participant в
активном standalone match блокирует старт с
`PLAYER_ALREADY_IN_ACTIVE_MATCH`. Отклонение не создаёт турнирные матчи и не
меняет status, `started_at`, bracket JSON/version или notifications.

### TOURNAMENT-013 Параллельность
Разрешены параллельные матчи, если один игрок и один судья не заняты одновременно в нескольких активных матчах. Параллельные результаты одной сетки сериализуются по tournament row и проверяют bracket version; каждый V2 node получает не более одного actual match.

### TOURNAMENT-014 Неявка/выход после старта
Ручная фиксация даёт техническое поражение в текущей паре и продвигает соперника.

### TOURNAMENT-015 Завершение
Формируются:
- места;
- сумма игровых очков по всем матчам;
- количество сыгранных матчей;
- топ-3.

Краткая итоговая зона показывает топ-3 после возникновения результата. Полные
итоги остаются доступными отдельно, поскольку место и сумма игровых очков —
разные показатели. Для остановленного турнира чемпион не объявляется.

Результат последнего матча, его статистика, bracket/champion transition и
уведомления фиксируются атомарно; сбой любого шага не оставляет частичный итог.

### TOURNAMENT-016 Остановка
Остановить может организатор. Указывается причина. Сыгранные матчи учитываются в статистике и рейтинге; несыгранные отменяются; победитель турнира и итоговый топ не формируются.

### TOURNAMENT-017 Детальная карточка
Показывает сетку, длительность, выделение линии текущего пользователя, активный матч, следующий матч и список итогов. Нажатие на матч открывает его детали.

### TOURNAMENT-018 Отмена до старта
Организатор может отменить турнир в статусах `collecting` / `bracket_generated` / `needs_regeneration`. Турнир переходит в `cancelled`, сетка сбрасывается, pending-приглашения помечаются cancelled. В истории остаётся как «Отменён», а не «вечный сбор».

### TOURNAMENT-019 Поддерживаемая версия DE-сетки

Новый игровой цикл double-elimination поддерживает только V2. Legacy V1 DE не
требует миграции, read/play compatibility или сохранения и при обращении должен
завершаться ограниченной по времени явной ошибкой unsupported version, а не
зависанием. Это правило не разрешает автоматический reset/recreate production:
любая такая операция выполняется только после отдельного явного разрешения с
точным target и планом проверки (ADR D25).

### TOURNAMENT-020 Иерархия карточки по фазе (D36/D37)

В `collecting` и `needs_regeneration` организатор видит действующие правила и
состав до построения или перестройки сетки; prestart edit и guards сохраняются.
В `bracket_generated` сетка и готовый следующий матч стоят перед повторной
read-only сводкой. В `in_progress` текущий/следующий матч и сетка предшествуют
вторичным операциям. В terminal состоянии показаны только действительные
результаты, с доступом к полным итогам; остановка не объявляет чемпиона.
Порядок не расширяет права organizer/participant/scoped admin, не добавляет
приглашения при D37 и не меняет сохранённые правила или сетку. Реализация
GAP-019 проходит последовательно двумя частями: pre-generation и
generated/active/terminal; полная приёмка требует обеих.

## 12. TEAMS — команды

### TEAM-001 Создание
Любой пользователь может создать неограниченное число команд и состоять в нескольких. Обязательное поле — название; аватар, слоган и welcome text опциональны.
Список команд является первым содержательным блоком. Единственная встроенная
форма создания раскрывается по явной команде и после успеха возвращает фокус к
созданной команде.

### TEAM-002 Капитан
Один капитан. Создатель становится капитаном.

### TEAM-003 Права капитана
- приглашать в команду;
- менять название, аватар, слоган, welcome text;
- исключать участников;
- передавать капитанство.

Исключение участника и передача капитанства требуют именованного подтверждения.
Неизвестный исход изменения настроек не повторяет запись автоматически: черновик
сохраняется, а отдельное чтение показывает текущее серверное состояние.

### TEAM-004 Приглашение
- TTL 14 дней;
- показывается в notification center;
- активное приглашение можно принять/отклонить;
- повторное приглашение — новая запись.

Email не используется.

### TEAM-005 Принятие
После принятия показывается экран приветствия команды.

### TEAM-006 Выход
Обычный участник выходит самостоятельно. Капитан сначала передаёт капитанство.

### TEAM-007 Автопередача
Если капитан заблокирован или удалён из команды без ручной передачи, капитаном становится текущий участник с самой ранней датой вступления. Он получает уведомление с игровым текстом.

### TEAM-008 Архив
Если участников не осталось, команда архивируется и исчезает из активных списков, сохраняя историю.

### TEAM-009 История
Выход не переписывает исторические матчи и турниры. Командный рейтинг строится по текущему составу.

## 13. NOTIF — уведомления

### NOTIF-001 Центр уведомлений
Отдельный экран, доступный с главной и из профиля. Карточка содержит дату/время, сообщение, статус и действия.
Фильтр «Актуальные» показывает доступное действие либо непрочитанную
нетерминальную карточку. Обычная карточка покидает фильтр только после
подтверждённого сервером `readAt`; приглашение с доступным действием остаётся.

### NOTIF-002 Типы MVP
- приглашение в матч;
- приглашение в турнир;
- приглашение судить;
- приглашение в команду;
- добавление в турнир командой;
- остановка матча/турнира;
- передача судейства;
- назначение капитаном;
- системные изменения доступа к аккаунту.

### NOTIF-003 Popup
Если пользователь находится в активной сессии и приглашение актуально, можно показать одну ненавязчивую шторку/диалог. Просроченное приглашение при следующем входе popup не вызывает.

### NOTIF-004 История
Устаревшая карточка остаётся и показывает причину: timeout, событие началось, отменено, завершено, состав закрыт.

### NOTIF-005 Read state
Хранится read/unread, но без агрессивных бейджей. Допустим один спокойный индикатор в точке входа.
Пока действует D37, скрытые игровые invitations не попадают в видимые списки,
popup и индикатор. Счётчик и отбор первых непрочитанных должны согласовываться
с видимой выборкой; team invitations и judge handover остаются доступными.
Batch-ответ меняет локально только возвращённые `id/readAt`; пропущенные строки
остаются непрочитанными. Terminal lifecycle имеет приоритет над запоздалым read.

### NOTIF-006 TTL
- матч/турнир/судейство: 10 минут;
- команда: 14 дней.

## 14. ONB — онбординг

### ONB-001 Первый запуск
Автоматически запускается один раз после первого успешного входа и смены временного пароля.

### ONB-002 Возможности
- показать Home с прямыми действиями матча/турнира, рейтинг, историю,
  уведомления, профиль и доступные контекстные переходы без удалённых tabs;

  отдельное «Закрыть обучение», без второго равнозначного перехода;

### ONB-003 Учебный матч
Пользователь создаёт учебный матч с системным участником «Призрачный Олег» и проходит judge flow.

### ONB-004 Изоляция
Учебное событие не влияет на историю, статистику, рейтинг и соперников.

### ONB-005 Повтор
Повторный запуск доступен из профиля.

## 15. HELP — FAQ и feedback

### HELP-001 FAQ
Категории и статьи; компактная справка по матчам, турнирам, подаче, рейтингам, командам и уведомлениям.

### HELP-002 Контекстные подсказки
Короткие подсказки в setup flow, judge mode и рейтинге.

### HELP-003 Feedback
Форма:
- категория: ошибка/идея/вопрос/другое;
- многострочный текст до 4000 символов в native textarea;
- просьба приложить материалы ссылкой.

Переносы строк сохраняются в отправленном и сохранённом сообщении. Поле имеет
начальную высоту 5 строк, только вертикальное изменение размера и ограничение
высоты 40vh. Известная ошибка сохраняет черновик и ждёт явного повтора; успех
очищает поле. Вложения не поддерживаются.

## 17. AUDIT — облегчённый аудит

Фиксировать только критичные действия:
- создание/изменение/блокировка пользователя;
- создание/старт/завершение/остановка матча;
- judge acquire/release/handover;
- создание турнира, генерация/роспуск/старт/остановка сетки;
- завершение турнирного матча;
- создание/изменение команды, membership и капитанство;
- invitation response/expiry;
- аварийная коррекция счёта.
- cancel standalone: actor, timestamp, prior state/version и опциональная причина;
- void результата: исходный результат/version, actor, timestamp, опциональная
  причина и идемпотентная компенсация; отдельного approval state нет.

Каждое очко хранится в match event log, а не дублируется в общем audit log.
Исходные события и записи void/compensation не удаляются и не изменяются задним
числом.

## 18. Definition of Done для требования

Требование завершено, только если:
- есть тесты до реализации;
- тесты проходят локально и в CI;
- покрыты happy path, error path и минимум один boundary case;
- API и UX состояния согласованы;
- миграции обратимо применяются на тестовой БД;
- нет нарушения read-only и permission rules;
- traceability matrix обновлена;
- нет flaky-тестов.
