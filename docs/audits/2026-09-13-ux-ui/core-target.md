# Согласованная структура основного пути

Статус: target принят Terra и координатором; см. [review](core-review.json). Приложение не изменено. Этот документ заменяет противоречивые варианты T-MATCH-CREATE/T-MATCH-DETAIL и уточняет соответствующие предложения пилота и JUDGE. Исходные пакеты и их доказательства сохраняются неизменными. Основание исправлений — [review MATCH](match-review.json). [Аннотированные схемы](core-wireframes.html) показывают одну колонку и согласованные точки входа.

## Создание: состав, правила, дополнительные параметры

Сохраняется принятая композиция [пилота](pilot/target-spec.md): одна колонка внутри текущего shell на desktop и mobile, без новой двухколоночной сетки и без sticky-кнопки. Порядок: заголовок и контекст challenge/revenge → формат и участие создателя → стороны A/B → сводка правил и раскрытие редактирования → сводка названия, судьи и приглашений с раскрытием → «Создать матч» и «Отмена». Название не возвращается перед составом. Первое игровое место видно на исходном экране390×844; весь парный состав не обязан помещаться без прокрутки.

Сводки всегда отражают текущий form state. Ошибка внутри закрытого раздела раскрывает его и переводит фокус к ошибочному полю. Сохраняются все режимы участников, правила, добровольные приглашения, purposeful prefill и текущая валидация. Непустые дополнительные возможности остаются рядом с соответствующей задачей, а не исчезают за безымянной иконкой.

### Быстрый выбор с явным назначением

Минимальное изменение сохраняет нынешнее назначение shortcuts — сторону B. Не вводится новый алгоритм выбора произвольной стороны.

- Группа находится непосредственно под стороной B и называется «Быстрый выбор для стороны B». Частые и недавние варианты явно подписаны как заполнение B1; доступное имя кнопки содержит имя человека и место назначения.
- Если B1 пусто, выбор человека сразу заполняет его. Если там другой человек или гость, появляется локальный предварительный просмотр замены с «Применить» и «Не менять». Повторный выбор того же ID ничего не меняет.
- Выбор команды всегда сначала показывает предварительный состав B1/B2 с конкретными именами. Сохраняются нынешние порядок и фильтры eligible members. В1×1 используется один участник; в2×2 — максимум два. Если второго допустимого участника нет, прежнее B2 не очищается скрыто: preview явно показывает, что там останется.
- Preview перечисляет все заменяемые значения и неизменяемые места. «Применить» изменяет только показанные места одним локальным обновлением. «Не менять» не меняет ничего. Изменение формата, eligibility или исходных мест делает preview устаревшим и требует построить его заново; старый preview не применяется.
- Команда с нулём допустимых участников не применяется; рядом объясняется причина. Не добавлять игроков, которых исключает обычный selector. Любое место остаётся доступно для ручного выбора через полный каталог или режим гостя.
- Пустые группы не оставляют рамку. Это локальные действия до общего submit, без нового API и без рассылки приглашений.

### Черновик и повторный вход

Обычный уход со страницы или Back уничтожает черновик по MATCH-015. Новое подтверждение ухода, localStorage и серверное сохранение не добавляются. Исключение AUTH-006/AT-AUTH-009/UX§3.1 сохраняется: runtime401 оставляет безопасное дерево формы смонтированным, скрытым и inert; тот же actor после входа получает прежние данные и путь без повторения mutation. Другой actor получает чистую форму. Pending и состояния каталога используют принятые общие контракты BUG-025/026.

## Детали матча: следующее действие по состоянию

Сначала сохраняется серверная видимость D17. Таблица ниже применяется только после разрешённого чтения detail; она не создаёт глобальный список активных матчей. D7 продолжает разрешать любому допустимому активному пользователю захват свободного места судьи через существующий допустимый вход. Блокировка аккаунта и ограничение одновременного судейства проверяются сервером.

Порядок экрана: заголовок/статус/refresh → счёт, участники и правила → состояние судейства и одно основное действие → остальные обычные действия → приглашения → журнал → отдельно исключительные операции → возврат. Пустой журнал — короткая строка, а не большая карточка перед действиями. Вся страница имеет текущий отступ под BottomNav; sticky-панель не вводится.

### Приоритет выбора действия

1. Конечное состояние обрабатывается раньше любых исторических ролей судьи.
2. Затем учитывается действующая reservation: адресат может принять, остальные видят ожидание и read-only вход.
3. Затем активный судья: если это другой аккаунт, доступен просмотр; если текущий аккаунт, доступен вход в ведение с обязательной проверкой устройства внутри JudgePage.
4. При свободном месте создатель waiting получает начало с ведением; остальные допустимые субъекты получают захват. Участие в матче не отменяет эти возможности.

`activeJudge.userId` в текущем GET не доказывает владение конкретной auth session: auth_session_id там не раскрывается. Поэтому MatchDetail не обещает «продолжить на этом устройстве» по совпадению userId. Вход называется «Открыть ведение»; существующий протокол JudgePage проверяет user+auth_session. На другом устройстве остаётся объяснение занятости и просмотр, без скрытого захвата. Home также не выводит право вести из historical judgeName/role.

| Состояние | Место судьи | Субъект | Основное действие | Дополнительные действия |
|---|---|---|---|---|
| waiting | свободно | создатель, включая создателя-игрока | «Начать и вести счёт» → существующий judge route и setup | «Начать без ведения» → нынешний start dialog; редактирование; просмотр |
| waiting | свободно | любой иной допустимый субъект с разрешённым входом | «Вести счёт» → judge route | просмотр; до начала ожидать старта организатором |
| in_progress | свободно | любой допустимый субъект | «Вести счёт» → judge route | просмотр |
| pending_confirmation | свободно | любой допустимый субъект | «Принять ведение и проверить результат» → judge route | просмотр предварительного результата |
| любое активное | reservation текущему аккаунту | адресат | «Принять ведение» → judge route | просмотр; срок и имя адресата видимы |
| любое активное | reservation другому аккаунту | все остальные | «Смотреть счёт» → judge?mode=readonly | объяснение передачи; у создателя сохраняются разрешённые операции |
| любое активное | активный судья — текущий аккаунт | субъект, независимо от участия/создания | «Открыть ведение» → judge route с проверкой auth session | просмотр; у создателя остаются его операции |
| любое активное | активный судья — другой аккаунт | все остальные | «Смотреть счёт» → judge?mode=readonly | имя ведущего; у создателя сохраняются его операции |
| finished/stopped standalone | не применяется | участник, включая создателя-участника | «Создать реванш» → существующий revengeOf | «Новая игра» → пустой manual /matches/new; назад |
| finished/stopped | не применяется | остальные активные читатели | «Новая игра» → пустой manual /matches/new | назад; read-only итог |
| cancelled либо иное конечное состояние без реванша | не применяется | активный читатель | «Новая игра» → пустой manual /matches/new | назад; объяснение состояния |

Во всех активных строках start остаётся только у создателя/организатора по D18 и только в waiting. Захват судейства другим человеком не даёт ему права начать матч. Нажатие «Начать и вести счёт» лишь открывает нынешний judge setup; создание, захват и старт не объединяются в новую транзакцию. Ошибки и гонки на входе сохраняют текущие guards и понятный путь к просмотру/повторной проверке.

Операции stop/no-show/cancel/void добавляются независимо от выбора primary по существующим actor/status/kind guards. Участие само по себе их не предоставляет. Cancel — D23, void — D24/D33; active admin не получает новый доступ к закрытому detail по этой задаче. Его отдельный recovery path остаётся на решении пакета ADMIN. Исключительные действия подписаны и сгруппированы отдельно; подтверждения и аудит сохраняются.

Приглашения остаются добровольными. T-MATCH-EDIT-INVITE предоставляет creator-only «Пригласить» для допустимого текущего участника без действующего приглашения, а не автоматическую рассылку после edit. Отмена старого приглашения удалённого участника корректна. Отказ/expiry/reinvite используют существующий API и terminal guards.

## Проверяемая приёмка

- Given пустая manual форма390, Then состав раньше редких настроек; desktop сохраняет одну колонку; CTA в потоке документа. Given все дополнительные возможности, Then каждая имеет подписанный вход и видимую сводку.
- Given shortcut и заполненное B1/B2, When подготовлен preview, Then показаны конкретные замены; отмена не изменяет draft, изменение исходных полей инвалидирует preview.
- Given runtime401, Then тот же actor восстанавливает безопасный draft без replay; другой получает чистый; ordinary Back уничтожает draft.
- Given free slot и participant/creator/creator+participant, Then судейский вход не потерян. Given reservation/occupied slot, Then нет скрытого takeover. Given тот же user на другом auth session, Then серверная проверка оставляет read-only и объяснение; score controls не включаются по одному userId.
- Given waiting не-создатель захватил слот, Then он ждёт старта создателем. Given creator+judge+participant overlap, Then primary выбран ровно один по таблице, все независимые разрешённые операции сохранены.
- Given finished former operator, Then blank новая игра доступна без clone/prefill. Given eligible revenge, Then purposeful маршрут остаётся отдельным и сохраняет правила D35.

Тесты: компонентная матрица всех строк/пересечений, браузерные390/1440 и narrow360, keyboard/focus, длинные имена, pending/error/401, реальные негативные actor/session ответы. Новый API или новые права не предполагаются. Изменение critical journey при реализации требует gate по AGENTS; исследовательские схемы сами по себе не являются реализацией.
