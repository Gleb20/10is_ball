# Версионирование Tab-10

Формат: **`MAJOR.MINOR.PATCH`** (три неотрицательных целых числа).
Канонический release gate — [WORKFLOW §7](WORKFLOW.md#product-versioning),
уточнение D4 принято 2026-09-18. Таблица ниже заменяет историческое правило
«любой новый flow = MAJOR»; архивные примеры и релизы не переписываются.

## Семантика цифр

| Цифра | Когда увеличивать | Примеры |
|-------|-------------------|---------|
| **MAJOR** | Несовместимый публичный контракт или поддерживаемый способ использования | Сломанный для существующих клиентов контракт |
| **MINOR** | Совместимая новая возможность, в том числе новый flow | Новый доступный пользователю сценарий без слома старого |
| **PATCH** | Исправление без новой возможности | Валидация, доступность, тексты ошибок |

## Правило сброса

При увеличении **левой** цифры все цифры **справа** обнуляются:

- `1.1.1` + **MINOR** (совместимый функционал) → **`1.2.0`**
- `1.2.3` + **MAJOR** (несовместимый контракт) → **`2.0.0`**
- `2.0.5` + **MAJOR** → **`3.0.0`**
- `1.0.0` + **PATCH** → **`1.0.1`**

Документация, тесты и повторный деплой неизменённого продукта не повышают номер.
Для пакета выбирают максимальный уровень по последствиям.

Исторический Phase 10 target с bottom bar superseded решением D36; уровень
будущего выпуска определяется фактической дельтой, а не прежней меткой Phase 10.

## Где фиксируется версия

- Корневой [`package.json`](../package.json) — поле `version` (источник для релиза)
- [`CHANGELOG.md`](../CHANGELOG.md) — пользовательский changelog по версиям
- [`docs/CHANGELOG_DEV.md`](CHANGELOG_DEV.md) — технический журнал шагов разработки
- Git-теги: `v{a.b.c}` (например `v1.2.0`)

## Связь с коммитами

Перед каждым разрешённым выпуском записать уровень и основание в release work
item. Разрешение на выпуск включает bump, без отдельного согласования номера.
