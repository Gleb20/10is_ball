# Fixtures для исследовательских пакетов

Этот документ задаёт подготовку локального стенда. Она не считается прохождением пользовательского сценария. Работать только с synthetic users в своей disposable DB, с указанными владельцем портами. До любой записи сверить loopback URL и `/health`: `release.environment=test`, candidate/build identity соответствует work order. Не копировать production data и не публиковать cookies, временные пароли или storage state.

## Разделять состояния

| Измерение | Что проверять | Что нельзя из этого выводить |
|---|---|---|
| Состояние аккаунта | `user.status` в ответе создания/admin read: active или blocked | Не выводить active из факта первого входа |
| Обязательная смена пароля | `mustChangePassword` | Это не статус аккаунта и не согласие на участие |
| Onboarding | Состояние текущего вошедшего пользователя | Его прохождение не означает согласие на матч/турнир |
| Участие | Фактическая сторона матча или строка roster | Создатель не обязательно игрок |
| Приглашение | Отдельная invitation row/status и политика турнира | Pending invite не означает inactive account |
| Управление счётом | Активная judge session/auth session | Передача физического телефона не создаёт другой аккаунт |

Координатор проверил на r3: только что созданный аккаунт, который никогда не входил, уже имеет `status=active`, `mustChangePassword=true` и присутствует в directory. [Runtime evidence](preparation-evidence/new-account-directory.json). Fixture `completeLogin=false` поэтому **не моделирует заблокированного или неактивного пользователя**. Для blocked-сценария требуется отдельное явное действие active admin на synthetic account и проверка результата.

## Кого подготовить

- Оператор C — обычный active user, вошёл и закончил обязательную смену пароля; в основном сценарии сам не играет.
- Игроки A/B — distinct active registered users, не занятые в другом active match. Не входить от них ради согласия в основном пути обычного матча.
- D — отдельный active account и отдельный browser context для передачи на другое устройство.
- Organizer, participant, invitee, outsider и active admin — отдельные fixtures там, где проверяются различия полномочий. Не выдавать оператору admin ради обхода неудобного экрана.
- Турнирный invitee для override — зарегистрированный active target без принятого invitation; отсутствие consent и состояние первого входа хранить раздельно.
- First-run account создавать отдельно от returning actor; не пропускать onboarding в сценарии, который исследует onboarding.

Fixture readiness подтверждается ответами API и требуемыми сохранёнными состояниями до начала измеряемого пути. Если нужная карточка отсутствует, проверить эти preconditions прежде чем ждать timeout.

## Имена, поиск и готовность экрана

Directory возвращает `displayName` в порядке «Фамилия Имя». Для технической установки fixture использовать уникальный фрагмент имени и фактический label из response/DOM, не собирать ожидаемую option перестановкой строк. Сохранять stable user ID для проверки записанного состава. Поиск полного имени в привычном пользователю порядке — самостоятельная UX-проверка; если он не находит человека, оформить наблюдение, не объявлять функцию удобной по техническому обходу.

После входа дождаться наблюдаемого перехода из `/login` и готовности auth state, затем открывать защищённую страницу. Не добавлять произвольный sleep. В новом default создания матча явно включать «Создатель играет» только в тех сценариях, где это необходимо по заданию. Одноимённые controls искать в подписанной группе своей стороны, а не глобальным `.first()`.

## Свидетельства и очистка

В `fixture-index.json` сохранять synthetic ID, label, роль, ожидаемые статусы, назначение и локальный runtime identity. Credentials/storage state держать отдельно в private temporary files и удалять после использования. Не сохранять секреты в screenshots, trace, logs или handoff. Если trace захватывает credentials, применить штатную sanitizer-процедуру до передачи evidence.

После пакета остановить только собственные процессы, удалить собственный disposable Compose project/DB и закрыть browser contexts. В handoff указать результаты cleanup. Ошибка fixture — не дефект приложения; ошибочную классификацию явно отозвать, а первоначальное отрицательное evidence сохранить.
