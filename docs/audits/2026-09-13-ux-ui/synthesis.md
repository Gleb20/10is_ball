# Синтез экспертного UX/UI прохода

Главный результат — интерфейс следует работе человека у телефона: выбрать игроков → проверить существенные правила → начать → вести и исправлять счёт → сохранить итог → подготовить следующую игру. Судейство не становится постоянной идентичностью человека, а приглашение не превращается в обязательную цифровую формальность.

Подготовительная модель GAP-012 реализована и принята локально на1257/1257 проверках. Все восемь исследовательских пакетов прошли review с обязательными исправлениями отчётов; дополнительный probe ручной коррекции принят. Рекомендации по интерфейсу ещё не реализованы. [Обзор постановок](review-index.html) формируется из единственного [BACKLOG](../../BACKLOG.md).

## Что сохраняется

Оба типа состава, зарегистрированные/гости/команды, нестандартные правила, добровольные вызовы и реванши, оба режима турнира, ручные перестановки и разрешённое включение, все способы завершения/передачи, история/рейтинг/профили/уведомления и административные функции остаются обнаружимыми. [Реестр22 групп](capabilities.md) содержит текущие и предлагаемые входы для108 требований. Наличие строки в реестре не означает полного runtime PASS.

Права и спортивные invariants не упрощаются вместе с интерфейсом. Account relationship отличается от владения auth session; текущий счёт сервера отличается от введённого draft; подтверждённый результат отличается от предварительного. История показывает обе стороны, поскольку ведущий может не играть. Одинаковые controls получают одинаковое поведение, но статус/роль/действие не сливаются в одну визуальную сущность.

## Что пока нельзя заключить

Пользовательское прохождение и интервью ещё не проведены. [Протокол](user-session.md) и пустая таблица наблюдений подготовлены; предположения о мотивах/переживаниях в [CJM](journey.md) обозначены гипотезами. Нет процента улучшения, средней скорости или обобщения на аудиторию по одному участнику.

Desktop/mobile здесь — browser viewports, не физические устройства. WebKit/Firefox, spoken AT, OS autofill/native select popup и настоящий browser zoom имеют явные ограничения. Точные проверенные и непроверенные ветки находятся в coverage.csv, requirement-coverage.csv и [каталоге состояний](component-state-index.md). CSS zoom/снимок полной страницы/статический код не выдаются за соответствующие runtime проверки.

Открыты Q-UX-001 (закрытие pending окна сетки), Q-UX-002 (модель аватара команды), Q-UX-003 (минимальный admin read по ID). Их задачи не ready. BUG-038 имеет принятый target-контракт; его миграции и runtime-проверки относятся к будущей реализации. Независимые улучшения от них не зависят. Полное завершение согласованного исследования требует участия пользователя; экспертная программа не подменяет этот этап.

## Как передавать задачу исполнителю

Передать exact baseline, одну canonical задачу, её mandatory correction/схему и acceptance evidence. Один writer на файл и стенд; минимальная подходящая модель; проверка source/current debt до изменения. Сначала meaningful failing evidence, затем bounded change и gates по риску. Reviewer проверяет сохранение возможностей и истинность доказательств; координатор принимает результат. Отчёт со слабым основанием возвращается с конкретной причиной, после двух повторений сужается scope или работу берёт координатор. Число findings не служит KPI.

Исходные package target-spec сохраняются для истории, но выдаются исполнителю только вместе с обязательными corrections и canonical BACKLOG. Локальная реализация, приёмка и публикация — разные статусы. Audit UI tasks не применяются к исходному dirty checkout и не выпускаются автоматически.
