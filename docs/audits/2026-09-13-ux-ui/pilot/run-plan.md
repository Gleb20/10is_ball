# Пилот координатора: компания у стола

Статус: **PLANNED — не evidence прохождения**. Входной gate: принятая GAP-012, frozen candidate manifest, production build из того же дерева, synthetic fixture и свободные собственные порты. Связь: TECH-006, SC-M01/M02/M03, SC-J01/J02/J03/J04. Формы результата — [templates](../templates.md); отдельного списка задач здесь нет.

## Сценарий и критерий успеха

«Анна и Борис хотят сыграть. Вы держите телефон, сами сейчас не играете. Запустите их матч, ведите счёт, исправьте ошибочное очко, сохраните результат и подготовьте следующую игру».

Исполнитель — обычный активный аккаунт оператора C. A и B — два других активных зарегистрированных игрока, не занятых в активных матчах. Имена и результаты синтетические. Оператор не получает admin-права ради облегчения сценария. Аккаунты A/B не открывают приложение для согласия. Вторая независимая сессия D предназначена только для проверки передачи на другой телефон.

Успех: в базе создатель C, фактические стороны A/B; приглашения не являются условием старта; сохранён точный счёт после Undo; C не попадает в статистику как игрок; после подтверждения доступен понятный путь к следующей игре. При сетевой ошибке исходное намерение не теряется и не дублируется.

## Последовательность экспертного прохода

| Шаг | Что фиксировать до действия | Наблюдаемый результат |
|---|---|---|
| Главная → начало | Первое видимое действие, соседние конкурирующие действия, смысл уведомлений | Найден вход в создание обычного матча |
| Состав | Положение A/B относительно правил и судейства; понятность собственной роли | Выбраны A/B, C не включён автоматически |
| Правила | Что предзаполнено, что обязательно; видно ли итог правил перед стартом | Правила понятны без раскрытия всех редких настроек |
| Старт | Количество переходов/подтверждений, требуется ли действие A/B | C получает судейскую сессию и запускает матч |
| Счёт | Визуальный приоритет счёта и +1, подача, сообщение о сохранении | Два быстрых намеренных +1 не склеиваются в одно |
| Ошибка | Где найти Undo; понятно ли, какое действие отменится | Одно ошибочное очко снято, правильные сохранены |
| Передача телефона | Требует ли UI назвать нового физического человека | Тот же аккаунт продолжает; attribution остаётся C |
| Передача устройства | Вход D, обнаружение передачи, ожидание, права старого устройства | После handover пишет только новая активная судейская сессия |
| Завершение | Отличие предварительного счёта от подтверждённого результата | Финальный счёт и участники совпадают в UI/API |
| Следующая игра | Следующий шаг без возврата к навигационному поиску | Можно начать новый матч; реванш сохраняет свой смысл |

Основной проход выполняется на 390×844 с viewport screenshots на каждом существенном шаге. Затем desktop 1440×900 с клавиатурой. Повтор затрагивает геометрию и взаимодействия; не трактовать два экспертных прохода как двух пользователей. Счёт шагов отражает интерфейс, время автоматизации не считается временем пользователя.

## Боковые проверки на отдельных fixtures

1. Нестандартные правила и 2×2: найти настройки, не пользуясь исходниками как навигационной подсказкой; проверить, что дополнительные функции обнаружимы. После наблюдения сверить перечень с capability inventory.
2. Добровольное приглашение: явно отправить, затем начать без ответа. Не включать это действие в измерение обычного пути у стола.
3. Временная потеря ответа записи счёта: сохранить видимый счёт/состояние, восстановить связь, сопоставить authoritative version и результат. Не симулировать успех локальным текстом.
4. Узкий экран 360px, landscape судейства, увеличение масштаба: отдельно записать способ масштабирования и ограничения. CSS zoom не объявлять browser zoom.

## Отчёт и эталон для пакетов

- `runs.csv`: отдельная строка на сценарий/viewport/роль/ветвь, наблюдаемые steps, PASS/FAIL/NOT_TESTED и причина.
- `report.md`: только наблюдения с evidence; отдельно экспертная интерпретация, альтернативные объяснения и открытые вопросы интервью.
- `findings.json`: общая причина и ссылки на COMPONENTS вместо повторного дефекта каждого поля; повторно проверить затронутые GAP-012 consumers.
- `target-spec.md`: порядок блоков, основное действие, путь к дополнительным настройкам, состояния и аннотированная схема 390/desktop. При неоднозначном продуктовом решении статус не ready.
- `flow-report.html`: current/target, ветви возврата, ошибки и передачи; версия и ограничения видны в самом файле.
- `handoff.md`: source/runtime identity, фактические проверки, покрытие функций, независимый verdict и условия dispatch остальных пакетов.

## Интервью после экспертного прохода

Выбрать максимум три спорные гипотезы, которые действительно влияют на приоритет или target. Сначала дать нейтральное задание без названий кнопок; уточнения о мотивах задавать после выполнения. Записывать успех, ошибки, возвраты и помощь. Высказывание одного участника служит качественным свидетельством, не оценкой частоты для всей аудитории. Интервью не заменяет проверку полномочий, данных или клавиатуры.
