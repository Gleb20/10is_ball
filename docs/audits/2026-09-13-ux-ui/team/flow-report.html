Краткий вывод

Проверены текущие маршруты капитана, участника, приглашённого, постороннего и бывшего участника на production-сборке из замороженного кандидата. Базовый жизненный цикл сохраняет данные и права. Подтверждённые проблемы находятся в подтверждении последствий, размещении ошибки и приоритете списка. MATCH-наблюдение не образует новый TEAM-дефект: оно дополняет GAP-013/F-MATCH-001. Предлагаемый поток меняет только порядок блоков, контекст обратной связи и подтверждение.

Текущий поток: создать и собрать команду

Источник шаблона: sharing + forms + empty states · Вход: Профиль → Команды

Шаги

  1. 1Профиль

    Карточка «Команды» ведёт в `/teams` и соответствует D5.

    Основное действие: Команды · Создание и приглашения → список.

  2. 2Раскрытая форма раньше списка

    Три поля и `Создать` всегда занимают верх страницы; список или пустое состояние находится ниже.

    Основное действие: Создать → активная команда, создатель становится капитаном.

    При ожидании POST кнопка недоступна, но поля остаются изменяемыми — подтверждение BUG-026.
  3. 3Detail команды

    Капитан видит состав, настройки, приглашение, выход и историю приглашений.

    Основное действие: Пригласить → ожидающее приглашение.

    При отказе PATCH общий alert появляется после всех карточек действий и вне области просмотра 360 px — F-TEAM-003.
  4. 4Предпросмотр и уведомления приглашённого

    Приглашённый видит ограниченную detail, затем принимает или отклоняет приглашение в уведомлениях.

    Основное действие: Принять → detail с приветствием.

    Отклонение и expiry дают конечную историю без действий. Ручной отзыв капитаном не предусмотрен текущим каноном.

Текущий поток: изменить состав и завершить участие

Источник шаблона: sharing + errors · Вход: active team detail

Шаги

  1. 1Состав капитана

    `Передать` и `Исключить` напрямую вызывают API-обработчики.

    Основное действие: Передать / Исключить → сохранённое изменение после одного нажатия.

    Промежуточного custom Dialog нет; это P2 safety-gap, а не доказанный необратимый P1.
  2. 2Прежний капитан становится участником

    Передача сохраняет нового капитана, прежний капитан остаётся участником.

    Основное действие: Выйти из команды → существующее подтверждение.

  3. 3Архив

    Ноль активных участников архивирует команду и закрывает ожидающие приглашения.

    Основное действие: К списку команд → только активный список.

    Бывший участник открыл историю по известному URL; необходимость отдельного входа не определена TEAM-008.

Предлагаемый поток: список → контекстное действие → безопасное последствие

Источник шаблона: forms + errors + sharing · Вход остаётся в Profile

Шаги

  1. 1Список активных команд первым

    `Мои команды` является первым блоком. Одна кнопка раскрывает существующую форму непосредственно под списком внутри `/teams`.

    Основное действие: Открыть команду → detail.

    Если список пуст → та же `Создать команду` раскрывает ту же встроенную форму.
  2. 2Ошибка внутри исходной карточки

    Ошибка и повтор настроек остаются внутри Settings; ошибка приглашения — внутри Invitations.

    Основное действие: Сохранить снова → повтор по явному действию.

  3. 3Именованное подтверждение

    Меню участника открывает отдельный Dialog исключения или передачи, называет человека и последствия.

    Основное действие: Подтвердить точное изменение → ответ сервера и обновление прав.

    Отмена или Escape → без записи, фокус возвращается к `Действия`.
  4. 4Быстрый выбор MATCH только для стороны B

    По принятому GAP-013 блок явно назначен стороне B; команда сначала показывает preview B1/B2 и замен.

    Основное действие: Применить → только показанные места B.

    `Не менять` оставляет черновик без изменений; новая произвольная сторона не вводится.
  5. 5Team grouping в TOURNAMENT с учётом policy

    При direct roster группировка только ускоряет поиск: добавить можно любого допустимого пользователя. При required consent отдельно обозначается teammate exception; для остальных различаются invite и подтверждаемый override.

    Основное действие: Выбрать конкретного пользователя → существующее подтверждение и серверная проверка.

    Ветка requireParticipantConsent=true не была проверена в TEAM run и требует отдельной fixture.

Открытые решения и припаркованные пункты

  • Принять отдельную модель аватара команды; D10 пользователя/гостя автоматически не переносится.
  • Принять или отклонить ручной отзыв ожидающего team invitation.
  • Решить, нужна ли пользователю обнаруживаемая история бывших/архивных команд; она не входит в готовую list-first схему.
  • WebKit, физическое устройство, 200% zoom, reduced motion, spoken AT, required-consent tournament и user session не проверены.
