## Турнирная команда не даёт нового исключения из consent

Фраза TS-TEAM-05 о «teammate exception» для consent=true неверна и отозвана. Current tournament-service addParticipant проверяет requireParticipantConsent || !isOrganizer для любого зарегистрированного игрока, независимо от общей команды. Общая команда меняет дополнительное уведомление tournament_team_added после разрешённого добавления, а не bypass подтверждения.

Разрешённое предложение F-TEAM-007 только про обнаружимость: группа «Из моих команд» в уже разрешённом выборе. В direct collecting organizer добавляет любого допустимого игрока; при required consent ручное добавление любого registered player, включая teammate, требует именованного override. Scoped non-organizer admin подтверждает всегда. Никакого обещания «сокомандник добавляется без подтверждения» и нового права. Это уточнение сохраняет D35, PRD005 и существующий сервер.

## Что можно передавать в bounded задачи

TS-TEAM-01: один inline create disclosure под списком текущих команд, без нового маршрута или истории. TS-TEAM-02: локальная ошибка настройки и отдельные remove/transfer подтверждения; request error должен отличать known rejection от unknown результата, не предлагать слепой retry после5xx. При disable отправки фокус не обещать удерживать на native disabledbutton: область прогресса получает programmatic focus только при потере предыдущего, после ответа фокус в локальном status/error. Меню участника не меняет права.

TS-TEAM-03 revoke — новая продуктовая гипотеза, текущий API не обещает эту функцию. TS-TEAM-04 avatar — отсутствие предусмотренной PRD возможности, модель ещё не определена; D10 не распространяется автоматически. TS-TEAM-06 исторический вход — гипотеза обнаружимости, не подтверждённое нарушение существующего контракта. Эти предложения не ready и не должны усложнять готовое list-first изменение.
