# Программа реализации — структура и зависимости

Сборка экспертного прохода всех пакетов; ADMIN, ручная коррекция и reset-контракт приняты. Пользовательское прохождение остаётся отдельным этапом. Канонические статусы, приоритеты и инструкции — только [BACKLOG](../../BACKLOG.md). Здесь ссылки и группировка, не второй список задач. «Кандидат спринта» не означает ready или обещанный срок. Размер/даты спринтов определяются после оценки исполнителем; часы и velocity не выдуманы.

## Уровни

Сценарий SC — задача человека в конкретном контексте. Эпик EP — устойчивый результат нескольких сценариев. История US — часть результата для определённого актёра. Задача AREA-NNN — самостоятельный проверяемый delta с одним владельцем. Подзадачи перечислены только в canonical задаче. Спринт объединяет готовые задачи для проверяемого результата, а не становится вложенным уровнем эпика.

## Как определяется приоритет

- P0: подтверждённая невозможность безопасно продолжать основную работу с серьёзной потерей/искажением данных либо критическим нарушением доступа. В пилоте таких находок нет.
- P1: основной сценарий блокируется для существенного способа взаимодействия или восстановление ненадёжно. BUG-029 — риск повторного начисления после подсказки, BUG-018 — клавиатурная/ARIA работа выбора; это не утверждение о доле аудитории.
- P2: подтверждённое препятствие с обходом, нечестное состояние либо обоснованная структурная рекомендация для важного сценария. Гипотезы явно отмечены; частота без данных неизвестна.
- P3: локальная несогласованность с небольшим последствием, после основных препятствий.

Сначала учитываются последствия и важность сценария, затем доказательство, охват общей причины и зависимости. Не считать число экранов числом пользователей и не выдавать экспертную уверенность за измеренную частоту. Количество найденных проблем не KPI агента; приёмка оценивает воспроизводимость, сохранение возможностей и однозначность инструкции.

## Ready gate

Один accepted target; конкретные входы и REQ/AT/ADR; роли/контракты/edge cases; понятный результат и GWT; named owner/write scope; проверка UI и persisted state по риску; документация/rollback; открытых продуктовых решений нет. Нереализованная зависимость может быть в очереди, но её контракт должен быть принят. Нельзя ставить ready, если задача всё ещё говорит «выбрать один из подходов» или её evidence отозвано.

## Очередь внутри S4

Спринт S4 разделяется на независимые пакеты результата: S4a — турнир (BUG-032/033, GAP-019/020/021); S4b — команда (BUG-034/035, GAP-022); S4c — история/профиль/уведомления (GAP-024, BUG-036/037); S4d — администрирование (GAP-026 → GAP-027 после приёмки). Это очередь инкрементов, а не обещание уложить всё в один период. В каждой задаче метка S4 candidate отсылает к этой очереди. Общие файлы компонентов изменяет один writer, затронутые consumers проверяются перед передачей следующему.

GAP-025 (аватар), BUG-022 (закрытие pending окна), GAP-028 (минимальный admin read) исключены до продуктовых решений. BUG-038 ready после reset-review, но требует полного contract/migration/PG/browser gate при реализации. Гипотезы TEAM про новые revoke/group/history features и RESULTS про URL persistence не превращены в обязательную разработку. Сохранённые возможности перечислены в capabilities и обязательных package corrections.

## Выход из каждого инкремента

Проверить пользовательский результат выбранных задач, их GWT, сохранение дополнительных входов и применимые состояния; выполнить package/browser/PG/full gates по каноническому риску; получить независимое review и приёмку координатора. Не переносить локальную верификацию на production. Принятый инкремент обновляет документацию и очередь, релиз требует отдельного scope. После этапа выделить ограниченную проверку существующего долга GAP-011/TECH-002 (WebKit/физические устройства/AT), сначала подтвердив актуальность остатка.
